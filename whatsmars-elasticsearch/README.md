### ES代替关系型数据库读写分离
对于关系型数据库，当读请求数远大于写请求数时，读请求会影响写请求的性能，此时我们常用的做法是读写分离。
数据库读写分离操作简单，但遇到跨表甚至跨库查询时，会受到分布式数据库中间件支持能力的限制，而且数据库也
无法承载海量数据的查询。此时应考虑同步写ES，对于实时性要求不高和那些复杂的查询直接走ES，少部分实时性
要求极高的请求仍走关系型数据库，这种情况下完全不用再做关系型数据库读写分离。

### ES集群的高可用

ES 集群的高可用不是简单地增加节点，而是依赖**集群管理节点多数派选举、主分片与副本分片、故障检测与自动恢复、跨故障域部署**共同实现。

#### 1. 集群管理节点的高可用

集群中只有一个被选举出的 cluster manager（集群管理节点），负责维护集群状态、创建或删除索引、分配分片等管理操作，不直接承载所有读写请求。

- 多个 master-eligible 节点通过多数派（Quorum）机制选举 cluster manager，避免脑裂
- 生产环境通常部署 **3 个专用 master 节点**，可容忍 1 个 master 节点故障；5 个可容忍 2 个故障
- 两个 master-eligible 节点无法在任意一个节点故障后继续形成多数派，因此不能获得同等的容灾能力
- cluster manager 故障后，其余满足多数派条件的节点会重新选举，无须人工切换主备

#### 2. 主分片与副本分片

ES 将索引拆分为多个主分片（Primary Shard），每个主分片可以配置多个副本分片（Replica Shard）。副本不仅用于容灾，也可以分担搜索请求。

- 写入请求先在主分片执行，再复制到对应的副本分片
- ES 会自动将同一分片的主副本分配到不同节点，避免单个节点故障同时丢失全部分片副本
- 生产索引通常至少设置 `number_of_replicas: 1`；副本数越高，冗余和读扩展能力越强，但存储与写入复制成本也越高
- 主分片不可用时，集群会从可用的副本分片中提升新的主分片，并在资源允许时重新创建副本，恢复冗余
- 如果某个分片的所有主副本都不可用，该分片对应的数据将无法读写

例如，一个索引配置 3 个主分片、每个主分片 1 个副本，共有 6 个分片，分布在多个数据节点上。任一节点故障后，只要每个分片仍有一个可用副本，集群就可以继续提供服务。

#### 3. 集群健康状态

- **green**：所有主分片和副本分片均已正常分配
- **yellow**：所有主分片可用，但仍有副本分片未分配；数据通常仍可读写，但冗余能力已经下降
- **red**：至少一个主分片不可用，部分数据无法访问，需要尽快处理

因此，**yellow 不代表集群完全不可用，但代表高可用能力已经受损**。

#### 4. 生产部署建议

- 将主分片和副本分片分布到不同机器、机架或可用区，并结合分片感知（shard allocation awareness）避免副本集中在同一故障域
- 跨可用区部署时，优先使用 3 个可用区，并将 master-eligible 节点分散部署，避免单个可用区故障导致多数派丢失
- 预留足够的磁盘、内存和计算资源，确保部分节点故障后，剩余节点仍能承接分片恢复和业务流量
- 客户端配置多个 ES 节点地址，避免请求入口依赖单个协调节点
- 定期执行快照（Snapshot）并验证恢复流程；副本用于节点级高可用，快照用于误删除、逻辑损坏和灾难恢复，二者不能互相替代
